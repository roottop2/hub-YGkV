# 运行说明

本文档只讲"怎么跑起来、怎么看结果"。
**产品要求以 `README.md` 为准，架构与编码约定以 `CLAUDE.md` 为准**，本文不重复它们。

---

## 1. 准备环境

```bash
# 装依赖（用 python_ai 环境）
pip3 install -r requirements.txt
```

密钥配置：把 `.env.example` 复制成 `.env`，填入自己的密钥。

```bash
cp .env.example .env
```

`.env` 里有四个关键项：

| 变量 | 用途 |
| --- | --- |
| `DEEPSEEK_API_KEY` | 所有 LLM 调用（规划 / 总结 / 审核 / 写报告） |
| `BOCHA_API_KEY` | Bocha 网页搜索 |
| `RESEARCH_MAX_ROUNDS` | 最多研究几轮，默认 3 |
| `LLM_RETRIES` | 模型输出异常时的重试次数，默认 3 |

> `.env` 已被 `.gitignore` 忽略，不会提交到 git。
>
> **注意**：`load_dotenv` 默认不覆盖系统环境变量。如果你的系统里已经设了
> `DEEPSEEK_API_KEY`，那生效的是**系统里那个**，不是 `.env` 里的。
> 拿不准就跑 `python3 -m backend.config`，它会打印每个密钥**来自哪里**。

## 2. 启动后端

```bash
bash start.sh                      # 默认 8000 端口
# 或指定端口
PORT=8001 bash start.sh
# 或直接用 uvicorn
python3 -m uvicorn backend.app:app --reload --port 8001
```

服务起来后 `GET /health` 会回显当前读到的模型、轮数和密钥来源。

## 3. 发起一次研究

研究要跑十几轮 LLM 调用和搜索，耗时几分钟，所以接口是
**"提交任务 + 轮询结果"**，不是一次请求等到底。

```bash
# ① 提交，立即返回 research_id（HTTP 202）
curl -X POST http://127.0.0.1:8001/api/research \
  -H 'Content-Type: application/json' \
  -d '{"topic":"低空经济在 2026 年的商业化进展"}'

# ② 轮询：每完成一步，返回的内容就长一点
curl http://127.0.0.1:8001/api/research/<research_id>

# ③ 报告生成后，直接看页面
#    浏览器打开 http://127.0.0.1:8001/api/research/<research_id>/html
```

**轮询能看到什么**：`process.steps` 一步步增加（规划 → 检索 → 总结 → 判断），
`draft` 一节节变长，`sources` 一条条累积。这就是 README 要的"研究过程记录"。

> 在 Windows 的 Git Bash 里用 `curl -d '{"topic":"中文"}'` 传中文可能被
> 终端编码搞坏（报 `There was an error parsing the body`）。
> 把 JSON 写进一个 UTF-8 文件，用 `--data-binary @body.json` 传就不会有问题。

## 4. 接口一览

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/health` | 健康检查 |
| POST | `/api/research` | 发起研究，返回 202 + `research_id` |
| GET | `/api/research` | 列出全部研究记录（轻量摘要） |
| GET | `/api/research/{id}` | 查单条研究，可轮询看进度 |
| GET | `/api/research/{id}/html` | 直接看报告页面 |

状态机：`pending → running → completed / failed`。
失败时 `error` 字段有原因，**已经写下的中间结果仍然保留**。

## 5. 产出物在哪

### 通过接口

- `report` —— 结构化研究报告（标题 / 摘要 / 分节正文 / 关键结论 / 遗留问题）
- `report_html` —— 上面的可视化版本，**自包含 HTML**（内联样式、零外部依赖，
  存下来双击就能看）
- `sources` —— 来源列表（URL / 标题 / 站点 / 日期）
- `process` —— 研究过程（检索了哪些关键词、读了哪些页面、迭代了几轮、每步做了什么）
- `confidence` —— 置信度说明（等级 / 分数 / 理由 / 信息截止时间 / 哪些是模型推断）

### 落盘

每次研究一个 JSON 文件：`backend/data/research/{research_id}.json`。
该目录已被 `.gitignore` 忽略。

## 6. 分模块自检

每个后端模块都有 `__main__`，可以单独跑。

**不需要网络和密钥**（随时可跑）：

```bash
python3 -m backend.config        # 配置自检（密钥打码 + 来源标注）
python3 -m backend.models        # 数据模型序列化与容错
python3 -m backend.storage       # 落盘读写（自建测试记录，跑完自动清理）
python3 -m backend.agent.base    # JSON 解析兜底 / 空输出重试 / 模板渲染
python3 -m backend.agent         # agent 包导出自检
```

**需要密钥和网络**（人工验证用）：

```bash
python3 -m backend.tools         # 单次 Bocha 搜索
python3 -m backend.agent.keyword # 生成关键词（1 次 LLM）
python3 -m backend.agent.summary # 总结搜索结果（1 次搜索 + 1 次 LLM）
python3 -m backend.agent.judge   # 判断是否补检（2 次 LLM）
python3 -m backend.agent.report  # 生成报告 + HTML（2 次 LLM）
python3 -m backend.engine        # 先跑离线控制流自检，再跑完整端到端
python3 -m backend.research      # 完整研究 + 落盘，带模拟轮询
python3 -m backend.app           # 打印路由表并启动开发服务器
```

> Windows 控制台默认 GBK，中文日志会乱码。
> 跑之前加个 `PYTHONIOENCODING=utf-8` 就正常了：
> `PYTHONIOENCODING=utf-8 python3 -m backend.models`

## 7. 设计上的几点说明

**为什么 agent 不调工具？**
四个角色 agent 都是**无工具的单次 LLM 调用**，只负责"想"。
"什么时候搜、搜完干什么、要不要再来一轮"全在 `engine.py` 里用确定性的
代码控制。这样流程可预测、可调试，也不会出现 agent 空转乱搜。

**为什么正文不让模型重新组织？**
报告正文由草稿段落直接映射（`heading` = 当初的搜索关键词，`body` = 那段总结）。
模型重写容易顺手编造，而且会断掉"正文 → 关键词 → 来源"这条追溯链。

**置信度为什么不让模型自评？**
让模型给自己的答案打分基本不可靠——它倾向说"很有信心"。
这里改成数客观事实：来源条数、站点个数、正文厚度，用软饱和曲线合成，
**上限 0.90 永不给满分**（一个由搜索摘要拼出来的报告，不该声称绝对确定）。

**为什么来源核实不到就丢弃？**
主笔给的关键结论会带上来源 URL。如果某个 URL 不在真实来源列表里，
说明模型可能是编的——直接丢掉并记 warning，而不是留着当"来源"。
核实不到来源的结论会被标注为「模型推断」。

## 8. 已知限制

- **置信度是启发式的**：它衡量的是"资料够不够多、够不够分散"，
  不判断资料本身可不可信（比如引用了内容农场，分数一样会高）。
- **不抓取网页正文**：总结基于搜索结果返回的摘要（Bocha 的 `summary` 字段），
  不是页面全文。摘要短的时候，正文深度会受限。
- **事实准确性依赖模型**：提示词明确要求"只写搜索结果里真实存在的信息"，
  但没有做二次核验，重要结论建议点开来源自己确认。
- **轮数与并发**：研究任务在进程内用 `asyncio` 后台跑，
  服务重启会丢失进行中的任务（已落盘的中间结果不丢）。
