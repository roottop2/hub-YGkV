# 技术路线的适用场景

> 版本：v1.0　|　日期：2026-08-13
> 本文档说明"基于知识图谱 + RAG（BM25 检索 + 大模型生成）"这套技术路线适合用在什么地方、为什么适合、不同场景怎么适配。

---

## 一、技术路线核心特征回顾

这套技术路线可以概括为一句话：

> **"离线把领域知识结构化（知识图谱），在线把用户问题先理解（意图+实体）、再检索（BM25）、最后生成（大模型）。"**

它同时具备三个能力，这正是它适用的判断依据：

| 能力 | 来源 | 价值 |
|---|---|---|
| **领域准确** | 知识图谱（结构化事实） | 回答有据可依，不靠大模型"猜" |
| **覆盖广、更新快** | 检索（BM25 + 图查询） | 新增商品/政策只改图谱，不用重训模型 |
| **自然流畅** | 大模型（Deepseek） | 生成人能听懂的完整句子 |

**判据**：一个场景同时满足"① 有大量结构化事实需要被问答 ② 要求答案准确、不能编造 ③ 知识经常变化"时，本技术路线就是强适配的。

---

## 二、适用场景一览

### 场景 1：电商客服问答（本项目的直接场景）★★★★★

- **问题类型**：商品参数、价格库存、订单状态、退换货政策、物流咨询；
- **为什么适用**：
  - 商品/订单/政策都是**结构化数据**，天然适合建图谱；
  - 答案必须**精确**（价格、订单号、状态不能错），纯大模型会幻觉，纯检索回答又生硬；
  - 商品上新、价格调整**频繁变化**，改图谱即可，无需重训；
- **落地方式**：客服入口嵌入本系统，冷门问题转人工（人机协作）。

### 场景 2：其他垂直行业客服 / 政策咨询 ★★★★★

- **行业**：金融（理财产品参数、手续费规则）、政务（办事材料、办理条件）、保险（理赔条款）、电信（套餐资费）；
- **为什么适用**：与电商同构——大量"事实型 + 规则型"知识、要求严谨、政策常更新；
- **差异点**：实体与关系定义不同（如金融的"年化收益率"、政务的"材料清单"），只需替换"实体/关系/意图"的配置与数据，**代码骨架复用**。

### 场景 3：企业内部知识库问答 ★★★★

- **场景**：员工问 HR 制度、IT 流程、财务报销规则、产品文档；
- **为什么适用**：企业知识分散在文档和系统里，检索 + 生成能把"答案出处"一起给出，降低合规风险；
- **差异点**：知识来源是文档而非数据库，需先做**文档结构化**（抽取成三元组或建立段落索引）。

### 场景 4：智能导购 / 商品推荐解释 ★★★★

- **场景**：用户问"有没有适合跑步的鞋？""小米手机和华为手机哪个便宜？"；
- **为什么适用**：图结构天然支持**多跳推理**（跑步 → 运动鞋 → 品牌 → 价格对比），比纯文本检索更能回答"对比类、筛选类"问题；
- **差异点**：检索结果需要更强的排序与过滤逻辑。

### 场景 5：数据中台的"问数"（NL2SQL 的替代或补充）★★★★

- **场景**：业务人员用自然语言查经营数据："上个月华东区销售额是多少？"；
- **为什么适用**：图谱把"指标口径、维度、表结构"语义化，检索到对应指标后再生成，能回答**口径类**问题；
- **差异点**：尾实体多为数值/时间，答案生成偏格式化。

## 三、不适用 / 需谨慎的场景（反例）

| 场景 | 为什么不适用 | 更合适的方案 |
|---|---|---|
| **开放式闲聊、创意写作** | 无固定事实，图谱无用武之地 | 纯大模型 |
| **无结构化知识的全新领域** | 建不出有意义的图谱，检索无内容可检 | 纯 RAG（文档检索）或大模型微调 |
| **超低时延要求（毫秒级）** | 检索 + 大模型生成有网络与计算延迟 | 纯检索 + 模板；大模型改用缓存 |
| **强主观内容（观点、评价）** | 答案没有"对错"，无法用事实约束 | 大模型 + 提示词工程 |
| **知识几乎不变的小规模固定问答** | 图谱 + 模型成本高于收益 | 直接规则 / 决策表 |

## 四、方案对比：为什么选"RAG + 知识图谱"而不是别的

| 方案 | 优点 | 缺点 | 适合 |
|---|---|---|---|
| **纯规则/决策树** | 快、便宜、可控 | 覆盖窄、写不完所有问法 | 几十条固定问答 |
| **纯大模型（直接问答）** | 自然流畅 | 幻觉、领域知识缺失、无出处 | 泛知识问答 |
| **大模型微调（领域训练）** | 领域化 | 知识变化要重训、仍有幻觉 | 风格/话术稳定场景 |
| **纯 RAG（文档检索 + 生成）** | 有出处、更新易 | 回答不了"多跳推理/结构查询" | 知识以文档为主 |
| **RAG + 知识图谱（本项目）** | 精确 + 结构化推理 + 更新易 + 有出处 | 需要建图谱、前期成本高 | **事实密集、多变、要精确**的垂直领域 |

## 五、适用场景决策清单（自查表）

准备用这套技术路线时，逐条打勾：

- [ ] 1. 领域内存在大量"一问一答的事实"（参数、状态、政策、规则）？
- [ ] 2. 答案要求准确，错误会造成损失或投诉？
- [ ] 3. 知识会持续变化（上新、调价、政策更新）？
- [ ] 4. 知识可以或已经结构化（数据库、表格、规则）？
- [ ] 5. 能接受首问有一定延迟（检索 + 生成，约 1~3 秒）？
- [ ] 6. 有（或准备申请）一个大模型 API 预算？

> 满足 1~4 且接受 5、6 的，本技术路线高度适配；4 条以下，建议退回"文档型 RAG"或"纯检索 + 模板"。

## 六、迁移到其他行业的操作路径

把本项目的电商实现迁移到新领域，只需改动四处，代码骨架不动：

1. **数据层**：换新领域的数据源与标注规范；
2. **配置层**：修改实体集合（`config.py` 的实体/关系/意图定义）；
3. **对话管理**：改意图 → 槽位 → 策略的流程树；
4. **提示词**：调整 Deepseek 的领域角色设定（如"你是金融客服助手"）。

迁移工作量集中在**数据与标注**，模型与流程代码可复用。
